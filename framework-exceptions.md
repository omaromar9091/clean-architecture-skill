# Framework Reality Checks — Pragmatic Exceptions

Real frameworks push back on pure layering. These are documented, deliberate compromises — not violations, as long as they're acknowledged rather than silently absorbed.

| Situation | Pure rule says | Pragmatic exception |
|---|---|---|
| ORM requires a base class or attributes on the model (e.g., EF Core `[Key]`, Django Model base class) | No framework imports in Entities | **Acceptable** if the attributes are purely structural/persistence metadata with no behavior coupling, AND the class still enforces its own invariants in plain methods. If the ORM framework forces inheritance from a base class that carries behavior (e.g., ActiveRecord-style `save()`), that's a real leak — use a separate persistence model + mapper instead. |
| Validation framework (e.g., `class-validator`, FluentValidation, Data Annotations) wants decorators on request DTOs | DTOs are just data | **Acceptable.** DTOs live at the Application layer boundary but are inherently a serialization concern; decorating them with validation attributes doesn't leak business logic — it leaks input-shape validation, which is arguably adapter-level anyway. Keep *business rule* validation (e.g., "an order needs at least one line") in the Entity, and *shape* validation (e.g., "email must be a string") on the DTO. |
| Framework's DI container wants a parameterless constructor or specific lifecycle hooks | Constructor-based dependency injection everywhere | **Acceptable** as a Layer 4 concern only. Don't let it dictate how Use Cases or Entities are constructed — wrap/adapt at the composition root. |
| CQRS / Vertical Slice Architecture instead of classic 4-layer Clean Architecture | Must follow the 4-layer model | **Not a violation — a variant.** CQRS and Vertical Slice architectures still obey the Dependency Rule (commands/queries don't depend on infrastructure details); they just organize folders by feature-slice instead of by layer-type. If the codebase already uses one of these, don't force it into the classic 4-folder layout — apply the Dependency Rule and SOLID principles within whatever structure already exists. |
| Serverless/FaaS functions where the "framework" IS the entry point (e.g., AWS Lambda handler) | Frameworks stay at the outer edge | **Acceptable.** Treat the handler function itself as Layer 4 — it should do nothing but parse the event, call a Use Case, and format the response. Resist the urge to inline logic "because it's just a small function." |

**The test to apply when unsure:** *if I swapped this framework/library out tomorrow, would this specific piece of code need to change?* If yes, and it also contains a business rule, that's a real leak. If yes, and it's purely mechanical/structural, it's an acceptable Layer 3/4 concern living close to Layer 1/2 for practical reasons.
